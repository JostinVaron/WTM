# AGENTS — Instructions for AI coding assistants and automated reviewers

This file tells AI assistants, code-review agents, and CI bots how to work on
this repository correctly. Read it before writing code or conclusions.

## 1. What this repository is

- `main` is the published, licensed, tested state. Sources live in
  [runtime/termux/](runtime/termux/); everything else is documentation and
  governance.
- License: software is [PolyForm Noncommercial 1.0.0](LICENSE) (source-available,
  **not** OSI-approved), documentation is [CC BY-NC 4.0](LICENSE-docs.txt). See
  [LICENSING.md](LICENSING.md). Do not propose relicensing or redistributing
  under other terms without the owner.
- The deployed prototype on the owner's phone may differ from the published
  runtime. Do not assume the deployed device runs the published code.

## 2. Ground rules for analysis

- **Verify against the current tree, not stale snapshots.** Several documents
  describe the pre-release prototype; if a statement conflicts with
  `runtime/` or with [docs/certification.md](docs/certification.md), the code
  and certification doc win. Cite file paths and line numbers.
- **Do not claim things the repo does not claim.** The project does not
  guarantee 2K60, 20 ms, "impenetrable" security, or hardware certification.
  The on-device certification ([runtime/termux/tests/device-smoke.sh](runtime/termux/tests/device-smoke.sh))
  is **pending**, not done.
- **Never fabricate evidence.** If you did not run a test or read a file, say
  so. Distinguish "documented", "tested", and "assumed".
- Distinguish the two runtimes: the **deployed prototype** (unauthenticated,
  described in SECURITY.md) and the **published hardened runtime**
  (`runtime/termux/server.py`). Findings about one do not automatically apply
  to the other.

## 3. Working with the code

- Tests: `cd runtime/termux && python3 -m unittest tests.test_server_security tests.test_server_live`
  (host Python 3.10+ with aiohttp 3.14.x). CI runs the same suites in
  [.github/workflows/ci.yml](.github/workflows/ci.yml) on every push and PR.
- The server is TLS-only and refuses to start without valid TLS material and
  an auth file; tests generate these in a temp dir. Never add a test that
  bypasses the security middleware.
- Scripts are POSIX-ish bash for Termux; keep `bash -n` clean.
- The browser clients are plain HTML/JS with no build step; validate inline
  scripts with `node --check` (see CI).
- Secrets: never add or regenerate real tokens, keys, or certificates to the
  repo. The sweep pattern in CI must keep passing.
- Backward compatibility: any runtime change must keep
  `load_server_config()`, `build_app()`, the `/healthz` contract, and the
  roles (`viewer`/`admin`) intact unless a breaking-change discussion happened.

## 4. Security review rules

- Threat model: [docs/threat-model.md](docs/threat-model.md). Findings must map
  to a threat and an asset; rank CRITICAL/HIGH/MEDIUM/LOW with confidence and
  line references.
- Known, accepted limitations (documented, not bugs): static shared tokens
  with client-side logout, self-signed certificates mitigated by fingerprint
  comparison, per-install credentials generated by `install.sh`.
- Do not test against the owner's live devices or network without explicit
  permission. Automated analysis must stay read-only and offline.

## 5. Governance

- Propose contributions through issues/PRs; follow
  [CONTRIBUTING.md](CONTRIBUTING.md) and the release policy in
  [docs/project-governance.md](docs/project-governance.md).
- Version bumps go in [runtime/termux/VERSION](runtime/termux/VERSION); releases
  are built from `v*` tags by [.github/workflows/release.yml](.github/workflows/release.yml).
- Report security issues per [SECURITY.md](SECURITY.md); never post
  secret-bearing proof-of-concept material publicly.

## 6. External-AI review records

When an independent AI reviews the repository, record a dated summary with
evidence and corrections in [docs/certification.md](docs/certification.md)
under "Independent external reviews". Example entry: date, reviewer model,
scope, findings, whether findings were based on a stale snapshot, and fixes
applied.
